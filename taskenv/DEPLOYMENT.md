# TaskENV deployment guide

This guide describes the repeatable TaskENV build and deployment flow. It is
kept independent of any one host or control-plane installation.

Host-specific sandbox IDs, template IDs, API URLs and keys, private registry
credentials, EasyTier secrets and addresses, and boot-time instance policies
belong in an operator-owned deployment directory outside this repository. Do
not add those values to TaskENV source or documentation.

## Build and install

Run builds as a normal user. The host installation script must run as root and
only updates the existing AgentENV-compatible installation after the artifacts
have been built and checked:

```bash
cargo build --release -p agentenv --bin server -p aenv --bin aenv
make -C tools-image TOOLS_VERSION=0.1.2-taskenv.3
bash taskenv/templates/fetch-desktop.sh
sudo bash taskenv/bin/install-host.sh
```

`install-host.sh` installs the one server and CLI, imports the versioned tools
drive, and preserves the existing state directory. It does not create or
delete sandboxes, templates, volumes, network overlays, or operator services.

## Template family

The supported Ubuntu 24.04 family is:

| Alias | Contents |
| --- | --- |
| `taskenv-ubuntu-24-04-base` | Full systemd, D-Bus, udev, envd and base tools |
| `taskenv-ubuntu-24-04-desktop` | Base plus Xfce/Xvfb, deskd, Selkies and Chromium |
| `taskenv-ubuntu-24-04-dev` | Base plus Git, Node LTS/nvm, Rust/rustup, official Go, uv and Docker tooling |
| `taskenv-ubuntu-24-04-dev-desktop` | Development tools plus the desktop suite |

Template IDs are generated by the server and must be discovered with
`taskenv template list --output json` after publication. Resource sizing and
registry references are deployment choices; the example recipes use 16 vCPU,
32768 MiB RAM and 131072 MiB disk.

The complete rootfs build sequence is in
[templates/README.md](templates/README.md). The recipes provision the guest
rootfs interactively and publish snapshots through the normal AgentENV API.
The tools drive remains read-only and is injected through the upstream
`[tools]` configuration.

## Create and use sandboxes

Authenticate the CLI against the target installation, then use an alias or
published template ID:

```bash
taskenv auth
taskenv start taskenv-ubuntu-24-04-dev-desktop --timeout 14400 -d
taskenv connect <sandbox-id> --gui
```

Use `--timeout 0` when a sandbox is intentionally permanent. A permanent
sandbox still needs an operator-owned lifecycle policy for host shutdown,
resume, deletion, and access control. Keep that policy outside the repository;
the repository supplies the generic CLI, server, templates and tests.

## Operator-owned extensions

Some installations need boot-time resume units, EasyTier instances, SSH
provisioning, private DNS or other host integration. Implement those in a
private deployment repository or in the host's `/etc` and `/usr/local` local
administration paths. Such files may refer to local sandbox IDs and credentials;
they must not be copied into this repository or its public artifacts.

## Validation

Run the checks appropriate to the change before deploying:

```bash
make fmt
make clippy
make test-unit
make test
make -C services test
```

Capability-dependent and VM tests require Linux, `/dev/kvm`, ublk and the
configured test dependencies. Use isolated test state and credentials as
described in `AGENTS.md`; never point tests at a live deployment.
